# v0.2 设计笔记：多 Agent 并行协作

## 这一版要解决什么

v0.1 中每个问题只能交给一个 Agent。"Compare CellViT with my notes on HoVer-Net" 需要同时查本地论文库（`library`）和阅读笔记（`notes`），
但路由器只能二选一，所以总有一半内容答不上来。

v0.2 只引入一个新想法：**一个问题可以拆给多个 Agent 并行处理，最后合并成一个回答**。
为了控制复杂度，这一版只做**互不依赖的并行**，不做"后一个 Agent 要用前一个 Agent 的结果"这种串行依赖（见"已知局限"）。

```text
START -> supervisor_node（拆分任务）
           └─ Send × N（1~4 个，并行）
                ├─ search_node  ─┐
                ├─ library_node ─┤
                ├─ notes_node   ─┼-> summary_node（合并汇总） -> END
                ├─ concept_node ─┤
                └─ reject_node  ─┘
```

## 关键设计决策

### 1. 为什么用 `Send`，而不是在一个节点里 `asyncio.gather`？

在一个 `multi_node` 里用 `asyncio.gather` 并发调用几个 Agent，改动最小，也能达到并行的效果。
但这样一来，并行过程就藏在一个节点里面：图结构里看不出哪些 Agent 参与了，LangSmith 里也只能看到一个节点。

`Send` 是 LangGraph 做 map-reduce 的标准写法。条件边不再返回一个节点名，而是返回一组 `Send`：

```python
def dispatch_tasks(state: State) -> list[Send]:
    return [
        Send(CATEGORY_TO_NODE[task["category"]], {"task": task, "user_id": state.get("user_id")})
        for task in state["tasks"]
    ]
```

同一步返回的所有 `Send` 会在同一个 superstep 里并行执行。它们全部完成后，下一个 superstep 中 `summary_node` **只运行一次**，
这是因为多条边指向同一个节点时，同一步里的多次触发会被合并。

从运行日志也能看到并行：两个 Agent 的开始日志都打印出来之后，才出现第一个结果。

```text
~~~~~~This is Library Agent~~~~~~
~~~~~~This is Notes Agent~~~~~~
[library] The details for CellViT are as follows: ...
[notes] Your notes on HoVer-Net are: ...
```

### 2. 为什么 `agent_results` 必须带 reducer？

v0.1 的 `agent_result: str` 是一个普通字段。并行以后，两个分支会在同一步写同一个 key，LangGraph 无法判断该保留哪一个，
于是直接抛出 `InvalidUpdateError`。

所以改成带 reducer 的列表，每个分支只返回自己那一条，由 `operator.add` 拼接起来：

```python
agent_results: Annotated[list[AgentResult], operator.add]
```

**原则：只要一个 key 可能被多个并行分支同时写入，就必须给它定义合并规则。**

顺带一提，并行分支完成的顺序并不固定。`summary_node` 会先按 `tasks` 的顺序把结果重新排好，再交给模型，保证每次输出的结构一致。

### 3. 为什么让路由器拆子问题，而不是把原问题发给每个 Agent？

如果每个 Agent 都收到完整的 "Compare CellViT with my notes on HoVer-Net"，`library` Agent 很可能会顺手去找 HoVer-Net，
`notes` Agent 也可能开始评论 CellViT。每个 Agent 都要自己判断"哪部分归我管"，对小模型来说，这比直接回答一个问题难得多。

所以路由器的结构化输出从一个类别，变成了一组任务：

```python
class TaskItem(BaseModel):
    category: Literal["search", "library", "notes", "concept", "other"]
    sub_question: str   # 只包含这个 Agent 该回答的部分，改写成独立的英文问题
```

实际拆分结果：

| 原问题 | 拆分结果 |
| --- | --- |
| Compare CellViT with my notes on HoVer-Net | `library`: What are the details of CellViT?<br>`notes`: What are my notes on HoVer-Net? |
| What is a Vision Transformer, and what did I note about CellViT? | `concept`: What is a Vision Transformer?<br>`notes`: What did I note about CellViT? |

Agent 节点通过 `Send` 收到的只有 `{"task", "user_id"}`（`TaskState`），不再读取 `messages[0]`。
这样每个 Agent 的输入边界很清楚：它只能看到自己的子问题。

代价是：**拆错就会丢信息**。如果路由器漏掉了问题的某一部分，后面没有任何环节能把它补回来。

### 4. 每个类别最多一个任务：写进提示词，并在代码里再检查一遍

"Compare CellViT and HoVer-Net" 应该拆成 1 个 `library` 任务还是 2 个？
`library` Agent 的提示词本来就允许它对每篇论文分别调用一次 `search_library`，所以 1 个任务就够了。
拆成 2 个反而会让两个 `library_node` 并行运行，重复检索，最后还要再合并一次。

这条规则写进了路由器提示词，但小模型不一定每次都遵守。所以 `normalize_tasks()` 在代码里再做一遍：同一类别只保留第一个任务。
同时，`RouteDecision` 用 `max_length=4` 限制任务数量，防止模型把一个问题拆得过碎。

这和 v0.1 中"用代码合并论文版本"是同一个原则：**能用确定性规则解决的，就不要交给模型。**

### 5. 为什么把汇总拆成单独的 `summary_node`？

v0.1 的 Supervisor 节点要经过两次，靠 `if state.get("agent_result")` 判断这次是来分类还是来汇总，
路由函数里也要写 `if state.get("final_answer"): return END`。只有一条分支时，这样写还算能看懂。

并行以后，多个分支都要汇合回来。如果还用一个节点承担两件事，就需要推理"所有分支是不是都回来了""这是第几次进入"，很难读懂。
拆成两个节点以后，每个节点只做一件事，图也变成了一条从左到右的直线，不再有回环：

- `supervisor_node`：只负责拆分任务
- `summary_node`：只负责合并结果

### 6. 为什么 Agent 节点不再写 `messages`？

v0.1 中每个 Agent 节点都会把自己的回答追加到 `messages`。并行以后，几个 Agent 的中间结果会按不固定的顺序写进对话历史，
与最终回答混在一起。v0.2 中 Agent 节点只写 `agent_results`，**只有 `summary_node` 写最终的 AI 消息**，对话历史里只保留用户真正看到的内容。

### 7. 并行下的失败处理：一个分支失败，不能拖垮其他分支

在 LangGraph 里，同一个 superstep 中只要有一个节点抛出异常，**整步都会失败**，其他分支已经算好的结果也会丢掉。
所以 v0.1 中 `ask_agent()` 捕获所有异常、返回 fail_text 的做法，在 v0.2 中变得更加重要：它保证每个分支一定能返回结果。

汇总提示词新增了一条规则：某一部分失败或被拒绝时，要明确告诉用户这部分没能回答，**不许用其他部分的内容或模型自己的知识去补**。

开发时正好遇到了一次真实的部分失败。"Find recent papers about foundation models for cell segmentation, and explain what Panoptic Quality measures"
被拆成 `search` 和 `concept` 两个任务，当时 OpenAlex 连续返回 503，于是：

- `search` 分支返回"检索服务暂时不可用"
- `concept` 分支正常给出 PQ 的解释
- 汇总回答分成两节：第一节如实说明论文没检索到，第二节给出 PQ 的解释

其他各环节的兜底方式：

| 环节 | 失败时的行为 |
| --- | --- |
| 路由器 | 回退为 `[{"category": "other", "sub_question": 原问题}]`，与 v0.1 一致 |
| 单个 Agent | 返回该 Agent 的 fail_text，不影响其他分支 |
| 汇总 | 用代码按 `### [类别] 子问题` 把各个结果拼起来直接返回，信息不会丢 |

## 已知局限

| 局限 | 例子 | 可能的方向 |
| --- | --- | --- |
| 不支持串行依赖 | "Find new papers related to what's on my to-read list" 需要先查 `notes`，再用结果去 `search` | 多轮规划：Supervisor 看过第一轮结果后再决定下一步 |
| 汇总时仍会"补全"信息 | 对比 CellViT 和 HoVer-Net 笔记时，表格里 HoVer-Net 的编码器一栏写了 "Convolutional Encoder (Implied)"，这是模型从 CellViT 的描述里推出来的，笔记里并没有这句话 | 更严格的汇总提示词；或者对比类问题同时让 `library` 查两篇论文 |
| 拆分质量只能靠肉眼判断 | 目前只有 2 个多 Agent 测试问题 | 建一组带标注的问题集，同时评估类别和拆分 |
| 单任务问题仍然会走一次汇总 | `concept` 的回答本来就可以直接给用户 | 只在多任务，或确实需要时才汇总 |
| 检索忽略 "recent" 这类时间要求 | 与 v0.1 相同 | 提取年份，作为 OpenAlex 的过滤条件 |
| 没有对话记忆 | 与 v0.1 相同。另外要注意：如果加入 checkpointer，`agent_results` 的 reducer 会把每一轮的结果都累加起来，每轮开始前需要清空 | checkpointer + thread_id |

## 思考题（下一版的起点）

1. 问 "Compare CellViT with my notes on HoVer-Net"，看看汇总表格里哪些格子的内容其实不在任何 Agent 的结果里。
   如果路由器让 `library` 同时查 CellViT 和 HoVer-Net，对比会更可信吗？这应该由路由器决定，还是由 `library` Agent 自己决定？
2. 试着构造一个需要串行依赖的问题，比如"根据我的待读列表推荐新论文"。现在的系统会怎么拆？
   要支持它，`Send` 还够用吗？图结构需要怎么改？
3. 并行让总耗时从"各 Agent 耗时之和"变成了"最慢的那个 Agent 的耗时"。在 LangSmith 里对比单任务和双任务问题的耗时，
   看看节省了多少，以及路由器和汇总这两次额外调用各自占了多少。
