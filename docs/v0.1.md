# v0.1 设计笔记：Supervisor + 4 个专业 Agent

## 这一版要解决什么

用最少的结构跑通一个完整的多 Agent 流程：**分类 → 交给一个 Agent → 汇总**。
复杂度参考 medical_multi_agent，把医疗场景换成科研场景。

## 关键设计决策

### 1. 为什么是 Supervisor 模式，而不是让一个 Agent 带所有工具？

一个 Agent 带 5 个工具也能工作，但这样有两个问题：

- 提示词会越来越长，每个工具的使用规则挤在一起，小模型更容易出错
- 无法针对每类问题单独做兜底，比如"检索失败"和"笔记服务挂了"的提示语就应该不同

拆开以后，每个 Agent 只关心一件事，提示词短，失败文案也能各自定制。代价是多了一次分类调用，也多了一个"分错类"的风险（见下文"思考题"）。

### 2. 为什么 Supervisor 要把论文库标题写进提示词？

`search`（上网找论文）和 `library`（问本地论文）的边界天然模糊。
"Tell me about CellViT" 该走哪个？如果路由器不知道本地库里有什么，就只能靠猜。
所以 `library_titles()` 会读取 `data/papers.md` 的 `##` 标题，动态拼进分类提示词。

这是一个很常见的业务问题：**路由器需要知道下游能力的边界，才能正确分流。**

### 3. 为什么 `user_id` 不让模型填？

`notes` Agent 的工具签名里没有 `user_id` 参数，它通过 `ToolRuntime` 从程序传入的上下文里读取。
如果把 `user_id` 设计成模型可以填的参数，用户说一句"查一下用户 2 的笔记"，模型就可能照做，这就是越权。
**原则：身份、权限类的参数由程序决定，不交给模型。**

### 4. 外部 API 的选型和失败处理：为什么从 arXiv 换成了 OpenAlex

`search` 最初用的是 arXiv API。开发过程中它大部分时间都返回 406，有时连续十几分钟全部失败。
406 响应的 body 是空的，也没有 `Retry-After`，服务端完全不说明原因。
最符合现象的推测是按 IP 限流：安静一段时间后的第一个请求能成功，之后连续失败，而且重试越多，恢复越慢。
但这个推测**无法证实**，而一个功能不能建立在无法确认的行为上。

于是换成了 OpenAlex：免费、无需 Key，官方明确允许每秒 10 次请求，实测稳定，覆盖范围也更广（包括正式发表的期刊论文）。
代价是它返回的摘要是倒排索引（单词 → 位置列表），需要用 `rebuild_abstract()` 还原。

失败处理分两层：

1. 请求失败时，把错误**以文本形式返回给模型**，而不是抛出异常，这样模型可以如实告诉用户
2. 提示词里写明"不许编造论文"，防止模型在拿不到结果时自己编出论文

排查 arXiv 时的两个教训：

- 我先后怀疑过 URL 编码、请求头、User-Agent，每次"改了就好了"，最后都证明只是碰巧赶上服务恢复。
  **外部服务的问题，要用多次、间隔开的对照实验来确认，不要被一两次成功误导。**
- 选外部依赖时，先看它的**稳定性、限流规则、错误信息是否清晰**。一个不说明失败原因的 API，再怎么加重试也很难用好。

### 5. 同一篇论文的多个版本：用代码合并，而不是交给模型

检索 "foundation models for cell segmentation" 时，CellSAM 出现了两次：2023 年的 bioRxiv 预印本和 2025 年的 Nature Methods 期刊版。
两者内容基本一致，分开列出会让用户以为找到了两篇论文。

处理方式：`merge_versions()` 把标题相同（忽略大小写和标点）的结果合并成一组，以最新版本作为主条目，
旧版本的日期和链接放在 "Older versions" 下面，信息不会丢。

为什么放在工具里用代码做，而不是在提示词里让模型去重？
"标题相同就是同一篇"是一条确定性规则，用代码实现每次结果都一样。交给小模型的话，这次能认出来，下次就可能认不出来。
**原则：能用确定性规则解决的，就不要交给模型。**

局限：预印本正式发表时如果改了标题，按标题就匹配不上，仍然会显示成两篇。

### 6. 为什么每个 Agent 都有 fail_text？

`ask_agent()` 会捕获所有异常并返回预设文案，保证图的每个节点都一定有输出，流程不会中断。
Supervisor 分类失败时默认走 `other`，汇总失败时直接使用 Agent 的原始结果。
**原则：任何一个环节失败，用户都至少能拿到一个诚实的回答。**

## 已知局限

| 局限 | 例子 | 可能的方向 |
| --- | --- | --- |
| 检索忽略 "recent" 这类时间要求 | "Find recent papers about X" 返回了 2014 年的高引用论文 | 让模型从问题中提取年份，作为工具参数传给 OpenAlex 的过滤条件 |
| 一个问题只能交给一个 Agent | "Compare CellViT with my notes on HoVer-Net" 需要同时用到 `library` 和 `notes` | 多 Agent 协作 / 并行 fan-out |
| 没有对话记忆 | 问完 CellViT 再问 "What about its limitations?"，系统不知道 "its" 指什么 | checkpointer + thread_id |
| 路由正确率只能靠肉眼看 | 目前只有 5 个测试问题 | 建一组带标注的问题集，量化准确率 |
| 汇总会多一次 LLM 调用 | `concept` 的回答本来就可以直接给用户 | 只在需要时汇总 |

## 思考题（下一版的起点）

1. 用 `python main.py -i` 问 "Compare CellViT and HoVer-Net"，看它被分到哪一类、回答质量怎么样。
   如果要正确回答，需要哪些 Agent 参与？这些 Agent 是先后执行，还是可以并行？
2. 试着构造 5 个 `search` 和 `library` 之间容易分错的问题。你会怎么修改分类提示词？
   怎么证明修改后确实变好了，而不是碰巧？
3. `concept` Agent 不带任何工具。它和直接问大模型有什么区别？它在系统里真正的价值是什么？
